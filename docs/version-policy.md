# 개발일지 버전 기준

프로젝트마다 `MAJOR.MINOR.PATCH` 세 자리 숫자로 관리함. 수정량이나 커밋 수보다 사용자에게 달라진 기능과 호환성을 기준으로 올림.

## 번호를 올리는 기준

| 구분 | 기준 | 예시 |
| --- | --- | --- |
| PATCH · 마지막 숫자 | 기존 기능의 오류 수정, 문구·색상·간격·배치·아이콘·애니메이션·입력 편의 개선 | `1.8.9 → 1.8.10` |
| MINOR · 가운데 숫자 | 기존 사용법과 데이터를 유지하면서 독립적인 기능을 추가함. 파일 내보내기, 기기 동기화, 공유, 새 저장·복구 기능 등이 해당함 | `1.8.10 → 1.9.0` |
| MAJOR · 첫 숫자 | 기존 데이터·사용 방식과 호환되지 않는 변경 또는 명시적으로 확정한 큰 제품 버전 | `1.9.0 → 2.0.0` |
| 공개 전 개발 | 기본 기능은 `0.1.0`부터 시작하며 작은 수정도 PATCH를 올림 | `0.1.0 → 0.1.1` |
| 첫 공개 | 핵심 기능을 다른 사용자가 공개 주소에서 이용할 수 있게 됨 | `0.x.x → 1.0.0` |

- PATCH는 소수점 한 자리가 아니라 정수임. `1.8.9` 다음은 `1.8.10`이며 `1.9.0`으로 넘기지 않음.
- MINOR를 올리면 PATCH를 0으로, MAJOR를 올리면 나머지 두 숫자를 0으로 시작함.
- 기존 버튼의 위치·모양·입력 동작을 다듬은 것만으로 MINOR를 올리지 않음. 구현 파일 수가 많거나 작업이 오래 걸렸다는 이유로도 올리지 않음.
- 같은 배포·같은 소스 변경을 여러 일지로 설명한 경우 같은 버전을 사용함. 서로 다른 후속 수정이나 배포를 같은 번호로 뭉치지 않음.
- 문서·기획·조사·아카이브 등록만 한 작업은 앱 버전을 새로 만들지 않으며 비워 둠. 배포 설정 정리도 앱 기능 변화가 없다면 버전을 올리지 않음.
- 기획이 아니라 실제 기능을 수정한 미배포 작업은 개발 버전을 부여할 수 있으나 요약과 다음 작업에 미배포 상태를 명시함. 테스트·검토만 했다고 새 기능 버전을 만들지 않음.
- 버전과 날짜를 따로 관리함. 하루에 여러 번 배포하면 같은 날짜라도 버전이 달라질 수 있음. 뒤늦게 일지를 정리했다는 이유로 작성일 순서에 맞춰 버전을 배정하지 않음.

## 기존 기록의 버전 수정

2026-11-12 사용자 요청에 따라 작은 수정에 MINOR를 올렸던 경우, 서로 다른 작업을 같은 번호로 묶었던 경우와 이후 번호를 정리했음. 기록 ID·작업 날짜·본문·프롬프트·출처·검증 결과는 보존함.

| 프로젝트 | 정리한 예 |
| --- | --- |
| MinLab | 명시한 전면 개편 `2.0.0` → 이미지 관리 기능 `2.1.0` → 3차 UI 개선 `2.1.1` |
| WorthIt | 목표·영수증 편의 수정 `1.0.2` → 이미지·PDF 내보내기 `1.1.0` → 사용 체크 개선 `1.1.1` |
| 미니어리 | 기존 UI 개선은 `1.8.1`부터 `1.8.12`까지 PATCH를 이어감. 기기 동기화 `1.9.0`, 코드 로그인·공유 `1.10.0`, 후속 오류 수정 `1.10.1 → 1.10.2` |
| MINOVA | 진행·디자인·문구 개선 3건은 같은 커밋·배포이므로 `1.2.3`을 함께 사용함 |
| MinSnakey | 경기장 위치 수정 `1.3.1` → 그리기·버튼 배치 개선 `1.3.2` |
| 미눔 | 사진·모델 기능 개발 `1.2.0` → 저장·실행 취소·복제 기능 개발 `1.3.0` → 거실 시각 개선 `1.3.1`. 세 작업의 미배포 표시는 유지함 |
| MinLab AI Office | 실행 안정성 수정 `0.5.32` → 이후 별도 반영한 계획·배정·추적 오류 수정 `0.5.33` |

기존 일지에 부여한 버전은 개발 과정을 일관되게 읽기 위한 아카이브의 버전 이력임. 원본 앱의 package.json·과거 Git 태그를 소급 변경하거나 실제 존재하지 않는 릴리스 태그를 만들지 않음. 원본에 확인 가능한 정식 릴리스 번호가 있으면 이를 우선 대조하고, 번호 충돌을 임의의 새 배포로 해석하지 않음. 커밋 번호는 버전 칸 대신 출처에 보관함.

## 기록 작성 방식

- 작업 목적과 실제 주요 변경, 이유, 확인 결과, 남은 일을 쉽게 작성함.
- 개발일지는 ‘~함·~했음·~필요함’ 문체로 작성하고 확인하지 않은 결과는 만들지 않음.
- 프롬프트는 관련 사용자 요청을 목적별로 묶어 서비스 맥락·작업 방향·요구·유지 조건을 갖춘 ‘~하세요’ 문단으로 작성함.
- 버전 수정만 요청한 경우 새 개발일지·프롬프트를 추가하지 않음.
