# 개발일지 버전 기준

## 번호를 올리는 때

버전은 프로젝트마다 따로 관리하며 `큰 변경.기능 추가.작은 수정`의 세 자리 숫자를 사용함. 기록 한 건마다 올리지 않고, 실제로 함께 반영한 작업은 같은 번호를 사용함.

| 구분 | 예시 | 번호 예시 |
| --- | --- | --- |
| 공개 전 기본 기능 | 앱의 첫 실행 가능한 기본 구조 | 0.1.0 |
| 공개 전 기능 추가 | 성장 도감 추가 | 0.1.1 → 0.2.0 |
| 오류·문구·색상·배치·예시 수정 | 계산 오류 해결, 문장 다듬기 | 1.0.0 → 1.0.1 |
| 새로운 기능·사용 흐름 추가 | 원본 문서 미리보기 추가 | 1.0.1 → 1.1.0 |
| 핵심 기능을 사용할 수 있는 첫 공개 | 다른 사람이 공개 주소에서 이용 가능함 | 0.x.x → 1.0.0 |
| 기존 사용 방식·저장 구조의 큰 변경 | 이전 기록을 그대로 사용할 수 없는 개편 | 1.x.x → 2.0.0 |
| 기획·조사만 진행 | 기능 아이디어와 요구사항 정리 | 버전을 비워 둠 |

단순히 저장소에 올리거나 문서를 정리했다고 새 버전을 만들지 않음. 같은 공개 배포를 준비한 점검·업로드·연결 기록은 같은 버전을 사용함. 개발일지에는 앱의 작업 버전을, 관련 커밋 번호는 원본 파일의 출처에 따로 보관함.

## 이번 기존 기록 정리 기준

이 번호는 기존 작업을 읽기 쉽게 묶은 **아카이브 정리 기준**임. 원본 앱의 화면·패키지 버전이나 과거 Git 태그를 변경했다는 뜻은 아님. 원래 번호와 내용은 Git 변경 이력에 남김. 작업 날짜는 유지하고 프롬프트는 서비스 맥락과 구체적인 요구를 담아 AI에 바로 전달할 수 있는 형태로 정리함.

- MinLab: 기본 저장소 구성 0.1.0 → 첫 공개·백업 확인 1.0.0 → UI·프롬프트·백업 개선 1.1.0 → 기록 연동 1.2.0 → 누락 기록·작업 날짜 수정 1.2.1. 로컬 환경 준비만 한 기록은 번호를 비움.
- NutriFit: 기본 기록 기능 0.1.0 → 기능 개선 0.1.1 → 성장 제한·진화·도감 0.2.0 → 첫 공개 배포 1.0.0 → 포만감·돼지 진화 1.1.0 → 기능 연결 오류 수정 1.1.1. 펫 기획 기록은 번호를 비움.
- ChoicePilot: 초기 기획은 번호를 비움. 공개 앱의 고민 정리 흐름을 완성한 기록은 1.0.0으로 정리함.
- 위험성평가서·작업계획서: 서식 분석은 번호를 비움. 일정 앱 연결 준비 0.1.0 → 로그인 없는 첫 공개 1.0.0 → 문서 미리보기·입력 기능 추가 1.1.0.
- WorthIt: 첫 공개에 함께 반영한 점검·저장소 구성·배포 기록은 모두 1.0.0. 이후 같은 작업에서 반영한 비교 예시 정리·계산·입력·백업 오류 수정은 모두 1.0.1.

## 기록 작성 방식

- 작업 목적: 어떤 불편이나 필요 때문에 시작했는지 한두 문장으로 작성함.
- 주요 변경: 실제로 바뀐 내용만 짧은 항목으로 작성함. 구상·계획은 구현 완료처럼 쓰지 않음.
- 확인 결과: 실제 확인한 범위와 남은 한계를 구분함. 검사 명령을 나열하기보다 무엇을 확인했는지 쉬운 말로 설명함.
- 다음 작업: 아직 하지 않은 작업을 ‘필요함·예정임·보류함’으로 적음. 완료한 것처럼 쓰지 않음.
- 프롬프트: 자연어 요청을 목적별로 묶고 서비스 설명·작업 방향·세부 요구·유지할 조건이 이어지는 문단으로 다듬음. ‘~하세요’ 문체를 사용하며 실제 요구 범위를 유지함. 결과 설명문이나 짧은 요청 나열, 고정 양식은 피함.
- 문체: ‘~함·~했음·~필요함’으로 통일함. 날짜·프로젝트·목적·변경·이유·확인 방법으로 6하원칙을 드러내며 모르는 사실은 채우지 않음.
