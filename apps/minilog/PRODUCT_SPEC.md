# MINILOG — 제품 및 개발 명세 v3.4
작성일: 2026-11-23
상태: 기획 확정 / 개발 착수 전

## 제품 정의
- 이름: MINILOG (미니로그)
- 목적: 네이버 블로그 광고 및 협찬 수익화를 위한 사진 중심 AI 원고 제작·운영
- 사용자: 두 명, **각자의 계정·각자의 블로그를 독립적으로 운영**. 콘텐츠/스타일/사진/수익/참고글은 절대 섞지 않음
- 배치: `minho-nim/MinLab`의 `apps/minilog/`, MinLab의 GitHub Pages 빌드에 통합
- 기본 흐름: 로그인 → 사진 다중 업로드 → 사진 분석 → 사실정보 확인 → 참고 스타일 반영 → 글/사진 배치 자동작성 → 개별 수정 → 승인 → 네이버 게시 보조 → 발행 URL 기록
- 네이버 외부 글쓰기 공식 API 지원 종료: MVP는 제목/본문 복사 + 사진 순서대로 다운로드. 비공식 자동 게시를 기본 기능으로 약속하지 않음

## 사용자 및 안전성
- 초대 기반 2개 계정; 로그인/로그아웃, 개인 블로그 주소·닉네임·카테고리
- Cloudflare Workers 인증(초대된 2인, 안전한 세션) + D1 데이터 소유자 검증 + 비공개 R2 객체 접근 정책으로 데이터 격리. 모든 API에서 사용자 소유권을 강제 검증
- GitHub Pages 프런트엔드 React/Vite/TypeScript, Cloudflare Workers + D1 + R2 백엔드. 사용자별 Gemini API 키를 이용한 서버 측 AI 호출
- 파일 업로드 크기·형식 검증, 오류 복구, 자동저장, 백업/복원, API 호출량 제한 및 비용 추적
- 참고 블로그는 허용된 공개 본문/직접 제공 원문만 분석; 문장 복제 없이 구성 패턴만 추출. 크롤링·접근 우회 금지
- AI는 사진에서 판단 불가능한 방문 경험·맛·가격·구매 사실·장소명을 허구로 채우지 않음. 정보 부족 시 확인 질문/빈 필드 유지
- 경제적 대가성 콘텐츠는 적절한 광고·협찬 고지 확인 전 승인 차단

## Gemini 계정·API 키 정책 (확정: 2026-11-23)
- 두 사용자는 **서로 다른 Google 계정**에서 각각 자신만의 Gemini API 프로젝트와 키를 발급한다. 각 사용자에게 할당한 **동일한 키를 Minially와 MINILOG가 공유**하며, 사용자별 공통 보안 설정에서 등록·교체·연결 해제한다.
- MINILOG는 전용 Cloudflare Worker, D1, R2를 사용하며 Minially와 **공통 인증·개인 Gemini 키 관리 계층**을 공유한다. Gemini 호출은 반드시 요청한 사용자의 키로 수행한다.
- 서로의 API 키, 사용량 내역, 청구 정보, 원고, 사진, 스타일 프로필에 접근할 수 없다. 키 원문은 화면에 다시 표시하지 않는다.
- API 키는 **브라우저 로컬스토리지·공개 GitHub 코드·D1 평문·로그에 저장하지 않는다.** 키 저장 시 Worker에서 AES-GCM 등의 인증된 암호화로 암호화하고, 암호화 마스터 키는 Cloudflare Worker Secret에 보관한다. D1에는 사용자 ID별 암호문·nonce·키 버전만 저장한다. 암호화 키 교체·키 삭제·복호화 실패 처리도 설계한다.
- 키 등록/갱신 요청은 HTTPS + 로그인 세션 보호 + 사용자 소유권 확인을 강제하고, 키를 수신하는 엔드포인트에는 민감 정보 로깅을 하지 않는다. 가능하다면 API 키 권한을 Gemini API로 제한한다.
- Google API의 무료 할당량과 과금은 사용자의 **Google Cloud 프로젝트 기준**으로 적용된다. 키가 다르다고 한도가 무조건 늘지 않으며, 별도 계정/프로젝트도 무료 사용이나 비용 0원을 보장하지 않는다.
- 두 앱의 Worker는 사용자별·앱별 요청 횟수/토큰/모델/오류/추정 비용을 `ai_usage_logs`에 저장한다. 프라이버시를 위해 사진·원고 본문·키는 로그에 남기지 않는다.
- 별도 Minoffia 통합 대시보드에서는 향후 MINILOG의 **집계된 운영 지표만** 권한 있는 관리자 API로 조회한다. Gemini 키를 Minoffia에 복제하거나 타인 계정 호출에 사용하지 않는다.
- 사용자 API 키가 없거나 유효하지 않으면 글 생성 기능만 제한하고, 저장 원고 조회·편집·내보내기는 계속 가능해야 한다.
- 두 사람의 API 키 분리 외에 사용량 초과, 호출 실패, 모델 미지원 시 사용자별 오류·재시도 정책을 갖춘다.

## Minially·MINILOG 공동 로그인 및 개인별 Gemini 연결 정책 (확정: 2026-11-23)
- **두 앱에서 각 사용자별로 동일한 로그인 자격 증명과 동일한 Gemini API 키를 사용한다.** 사용자 A는 앱 2곳에서 A의 Gemini 프로젝트/키를 사용하고, 사용자 B는 앱 2곳에서 B의 Gemini 프로젝트/키를 사용한다. A/B 간 키·계정은 공유하지 않는다.
- 공통 인증 서비스(예: 별도 Cloudflare Worker)를 하나 운영해 고유 `user_id`를 발급한다. 두 앱은 같은 인증 서비스를 신뢰하며, 각 앱의 서버는 발급된 세션/토큰의 사용자 및 앱별 접근 권한을 검증한다.
- **'로그인 코드 통일'은 동일한 계정으로 로그인하는 것을 뜻하며, 두 사용자가 같은 비밀번호나 단일 공통 PIN을 쓰는 구조는 금지한다.** 비밀번호는 해시 저장, 세션은 짧은 수명과 갱신/폐기 기능 제공, 로그인 시도 횟수 제한. 필요시 초대형 이메일 인증/패스키 이용.
- Gemini API 키는 공용 인증/비밀정보 보관 기능에서 사용자별로 1회 등록·회전·삭제한다. 두 앱 모두 서버를 통해 자신의 키로만 AI 호출한다. 클라이언트에는 키가 전달되지 않는다.
- MINILOG 전용 Worker와 Minially 전용 Worker는 분리하고, 공통 인증/키 관리 Worker에 서버 간 인증으로 연결하거나 이에 준하는 중앙 키 관리 구조로 구현한다. 브라우저가 다른 앱의 세션을 임의 재사용하도록 하지 않는다.
- 개인별 Gemini 프로젝트 사용량 한도는 **두 앱 호출량을 합쳐서 적용**된다. MINILOG·Minially 출처 앱, 모델, 토큰, 성공/실패, 추정 비용을 분리 기록하고 사용자별 및 앱별 쿼터를 제공한다.
- 인증 정보·키 저장소와 앱 콘텐츠 저장소는 분리한다. MINILOG의 원고·사진·참고 블로그·협찬 정보는 Minially에서 조회할 수 없고, 반대도 동일하다.
- 기존 Minially 로그인/배포 구조는 현재 소스 분석 후 마이그레이션한다. 기존 세션/이용 데이터를 파괴하거나 사용자 동의 없이 변경하지 않는다.
- GitHub Pages 도메인과 Cloudflare Worker 도메인이 달라질 수 있으므로 세션 쿠키, CORS, CSRF 방어 및 OAuth/이메일 로그인 리디렉션을 실제 도메인에 맞게 설계·시험한다. 공통 인증이란 자동 SSO를 보장하는 의미는 아니다.
- 통합 Minoffia 운영 대시보드에는 관리자 인증을 거친 **집계 지표만 제공**하며 개인 키, 원고, 사진은 전달하지 않는다.

## 사진 저장소 정책 (확정: 2026-11-23)
**기본 정책:** 게시 완료 확인일로부터 **30일** 보관 후 정리. **원본 정리 옵션 사용**, **삭제 예정 알림 사용**. 이 정책은 두 사용자 각각에게 독립적으로 적용한다.

### 게시 확인과 보관 기간
- 사진은 업로드 직후부터 사용자의 소유로 저장하며, 작성 중/검토 중/승인 대기/발행 준비 원고에 연결된 파일은 자동 삭제하지 않는다.
- `게시 완료` 상태는 사용자가 실제 네이버 게시글 URL을 등록하고 게시 완료를 명시적으로 확인한 경우에만 허용한다. 단순 AI 작성 완료, 앱 내 승인, 발행 패키지 다운로드는 게시 완료가 아니다.
- `published_confirmed_at`을 서버 시각으로 기록하고, 사진 정리 예정일 `delete_after_at = published_confirmed_at + 30일`로 계산한다. 예정일 전에는 삭제하지 않는다.
- 사용자가 게시 완료 확인을 취소하거나 원고를 미게시 상태로 되돌리면 자동 삭제 예약을 중단한다.
- 한 사진이 여러 원고에서 참조되고 있다면 모든 연결 원고의 보관 조건이 충족될 때까지 삭제하지 않는다. 협찬 계약 또는 사용자 보관 지정 파일은 정책에 따라 별도 보류할 수 있다.

### 원본 정리 옵션 (사용)
- 원본은 업로드 시 이미지 미리보기/분석용 최적화본을 만들되, 사용자가 원본을 직접 보관할 책임이 있다는 안내를 표시한다.
- 원본 자동 정리 대상 지정은 **업로드 완료, 처리 성공, 내보내기/로컬 백업 안내 확인** 이후로 제한한다. 원본만 먼저 없애 발행용 화질이 손상되지 않게 한다.
- 게시 완료 후 30일 정리 시 원본과 파생본(미리보기/압축/편집본)을 함께 정리하되, 다른 게시물에서 공유하는 객체는 참조 관계를 검사한다.
- 앱에서 삭제한 사진은 원고 미리보기에서 더 이상 표시되지 않을 수 있으므로, 글 본문·캡션·사진 순서·원본 파일명·게시 URL·이미지 삭제 이력 등 비이미지 메타데이터는 유지한다.

### 삭제 예정 알림 (사용)
- 사용자별 대시보드 및 저장소 관리 화면에 7일 전부터 삭제 예정 건수, 예상 삭제일, 해제/보관/다운로드 선택지를 표시한다.
- 초기 MVP에서는 앱 내부 알림을 우선 제공한다. 푸시/이메일 발송은 발송 채널을 명시적으로 설정하고 동의를 받은 후 도입한다.
- 게시 30일이 지났더라도 삭제 전에 다시 소유권, 사용 여부, 보관 예외 및 취소 여부를 검사한다.
- 삭제가 진행 중일 때는 원고를 별도 잠금/정리 대기 상태로 관리하고, 삭제 실패 시 재시도 가능한 상태 및 오류 이력을 남긴다.

### 사용자별 독립 저장과 보안
- 비공개 Cloudflare R2 객체 경로는 `{user_id}/{article_id}/{photo_id}/...` 등 사용자 소유를 명확히 구분한다.
- 사진 메타데이터 및 삭제 작업은 `user_id`를 기준으로 인증된 Worker가 소유권을 검증한다. R2는 공개 버킷으로 열지 않고 인증된 프록시 또는 단기 서명 URL로 접근한다.
- 자동 삭제 처리기는 **본인 소유 파일만** 정리하고 해당 객체를 참조하는 다른 사용자나 원고가 없는지 검증한다. 일반 사용자가 타인의 파일 경로나 삭제 대상을 조작할 수 없도록 한다.
- 두 계정의 저장 용량, 삭제 예정 내역, 삭제 로그 및 보관 예외 설정은 서로 노출되지 않는다.

### 실제 삭제·복구 안전장치
- 기본은 게시 후 30일에 삭제 대상 표시 → 검증 → 서버 측 파일 삭제 → DB 상태 확정 순서. 가능하면 먼저 복구 가능한 유예/격리 단계를 두되, 격리본도 Storage 용량을 차지하는 점을 UI에 명시한다.
- 저장소 객체 삭제 성공 여부를 확인하기 전에 DB에서 원고나 참조 정보를 삭제하지 않는다. 객체만 삭제됐거나 메타데이터 업데이트에 실패한 경우 재시도와 정합성 점검을 지원한다.
- 최종 삭제 후 복구는 보장하지 않으며, 별도 다운로드/백업 여부를 확인하게 한다. 30일 도달 시 무조건 복구 가능하다고 표시하지 않는다.
- 서버 예약 작업(Cron)이 없는 MVP 단계에서는 로그인/대시보드 접속 시 정리 대상을 안내하고 **사용자가 직접 정리 실행**한다. 자동 삭제는 서버 측 예약 작업 및 감사 로그가 완성된 뒤 활성화한다.

### 저장 용량 관리
- 개인별 사진 원본/최적화본/삭제 예정 파일 사용량을 집계하고, 프로젝트 전체 사용량도 관리자가 확인하도록 한다(다른 사용자 세부 자료 제외).
- 1인별 저장 상한·단일 파일 크기·사진 수·원고별 사진 수를 설정할 수 있게 하고, 제한 도달 시 신규 업로드 전 압축/정리를 안내한다.
- 클라이언트 업로드 전 리사이즈·적절한 압축을 적용하고 화질/회전/EXIF 제거 여부를 확인한다. 원본 보관 시 추가 점유 용량을 별도로 표시한다.
- Cloudflare R2/D1/Workers 무료 한도는 동일 계정의 다른 앱(Minoffia, Minially)과 공유될 수 있으므로 MINILOG와 계정 전체 사용량을 함께 확인한다.
- 저장소 데이터 삭제는 **Cloudflare R2 API를 통해** 수행하고 성공을 확인한다. D1 메타데이터만 지워서 실제 사진 용량이 정리된 것으로 취급하지 않는다.

### 데이터 필드 및 테스트
- `articles`: `published_url`, `published_confirmed_at`, `publishing_status`.
- `article_photos`: `user_id`, `storage_path`, `original_path`, `optimized_path`, `byte_size`, `delete_after_at`, `deletion_status`, `deleted_at`, `retention_override`.
- `photo_deletion_logs`: 요청자/대상 소유자/대상 파일/예약일/시도일/결과/오류 코드.
- 필수 검증: 두 계정의 데이터 분리, 미게시 사진 보호, 정확한 30일 시점, 보관 예외, 공유 파일 참조 보호, 알림 표시, 일시적 API 실패 후 재시도, 삭제 후 원고 메타데이터 유지.

## 1단계: 사진 기반 AI 원고 작성 MVP
**목표:** 사용자별 사진+간단한 사실 입력으로 사진이 배치된 원고 생성, 수정, 승인, 발행 준비 완료
- 사용자별 로그인 및 프로필, 인증된 Workers의 D1 소유권 검증과 비공개 R2 객체 접근통제
- 사진 여러 장 업로드, 미리보기, 수동 순서 재배치, 압축/메타정보 관리, 저장
- AI 사진 분석(무엇이 보이는지 식별), 사진별 메모/설명
- 글 유형: 카페/맛집/여행/제품 후기/정보 글/협찬
- 장소명/제품명/방문일/메뉴/가격/실제 소감 등 필수 사실 입력. 누락 사실 질문
- 개인별 참고 블로그 URL/예시 원문 등록; 제목·문단·사진·문체의 구조 분석 (접근 실패 시 직접 붙여넣기)
- AI 제목 후보, 개요, 본문, 사진 위치/캡션, 해시태그 생성; 금지 표현·출처 검토
- WYSIWYG 원고/사진 통합 편집기, 문단 재작성, 자동 저장, 버전 관리
- 초안→검토→승인→발행준비→게시완료. 승인 전 게시 방지
- 제목/본문 복사, 번호 붙은 사진 ZIP, 이미지 삽입 순서 안내. 네이버 게시 URL 등록
- 협찬 유형별 경제적 이해관계 표시 점검
- 완료 기준: 두 계정이 독립적으로 사진 올려 각자 글 1개씩 생성·수정·승인·내보내고 서로의 데이터를 볼 수 없음

## 2단계: 개인화 및 수익형 블로그 운영
**목표:** 개인 문체를 누적 학습(모델 재훈련이 아니라 규칙/예시 추출), 트렌드 발견 및 협찬 캠페인 관리
- AI 초안과 사용자 수정본 비교해 사용자별 스타일 프로필 개선
- 내 글/참고 글 반영 우선순위(초기 참고 글, 점차 내 글 우선)
- 실제 데이터 기반 키워드/검색 트렌드/검색 결과 비교; 조회수와 추정 지표는 혼동하지 않음
- 중복 주제 탐지, 개인별 콘텐츠 캘린더
- 협찬 캠페인: 제공사/제품/금전·현물 제공/마감/요구 키워드·사진/광고 고지 체크
- 썸네일, 리사이즈, 워터마크 등의 사진 편집
- 개인별 광고료·제품 제공·제휴 수익 기록 및 게시글 성과 수동 입력
- 완료 기준: 두 사용자 각각의 문체 프로필·협찬 활동·수익을 독립적으로 관리하고 다음 원고에 반영

## 3단계: 입력 보조·운영 자동화·성과
**목표:** 승인 뒤 에디터 입력 수작업 감소, 예약 초안, 실적 분석 및 협찬 역제안
- 네이버 스마트에디터 ONE의 변화와 서비스 정책을 검토한 뒤 크롬 확장 등으로 제목/본문/사진 입력 보조 실험; 최종 게시 클릭은 사용자
- 사진 순서/서식 유지 검증. 자동 게시 성공을 가정하지 않음
- 서버 예약 작업으로 승인 대기 초안 생성(승인 없는 무인 게시 제외)
- 사용자별 조회수·유입·공감·수익 분석(실제 수치 우선)
- 성과 기반 주제·기존 글 링크 추천, 협찬 분석, 월간 보고
- **협찬 역제안 시스템:** 사용자별 제휴 희망 매장·브랜드 후보 등록, 공개된 공식 제휴 연락 경로 기록, 자신의 실제 콘텐츠 성과·카테고리를 기준으로 적합성 분석
- **AI 맞춤 제안서:** 업체에 맞는 제안 이메일/문의 원고, 제공 콘텐츠·일정·조건·차별점 제안. 근거 없는 조회수/성과는 작성 금지
- **개인별 미디어킷:** 대표 게시글, 실제 조회수 및 방문 지표, 사진 샘플, 주요 주제, 협찬 조건을 PDF/공유용 자료로 정리
- **역제안 파이프라인:** 후보 → 조사 → 제안서 준비 → 사용자 승인 → 발송 → 회신 → 협의 → 계약 → 제작 → 완료/거절. 담당자·연락처·이력은 사용자별 비공개
- **전송 정책:** 제안은 각 사용자의 검토·승인 후 공식 연락 채널로 수동 발송하거나 연결된 이메일 서비스에서 승인 후 발송. 무차별 대량 자동 메일 발송 제외
- 완료 기준: 사진→AI 초안→승인→네이버 입력 보조→실제 게시 확인 및 개인별 성과 추적

## 기술/데이터
- UI: React + TypeScript + Vite, 기존 MinLab 디자인과 독립 앱 구조
- 배포: GitHub Pages `/MinLab/apps/minilog/` (기존 빌드에 앱 아웃풋 복사 필요)
- 계정/DB/미디어: Cloudflare Workers 인증, D1(SQLite) 사용자별 소유권 제어, 비공개 R2 사진 저장
- AI 백엔드: MINILOG 전용 Cloudflare Worker + 공통 인증/키 관리 계층 (사용자별 암호화된 Gemini 키, 인증된 유저 검증, 앱별·사용자별 rate limit, 호출 기록)
- 데이터: shared_auth_users, user_ai_credentials, ai_usage_logs, profiles, blog_references, style_profiles, articles, article_photos, article_revisions, photo_deletion_logs, sponsorships, revenue_records, article_metrics, outreach_leads, outreach_proposals, outreach_events, media_kits
- 보안: 공개 저장소에 비밀 키/개인 사진/협찬 계약서 직접 커밋 금지

## 첫 구현 순서
1. `apps/minilog` 기본 페이지/라우팅과 MinLab 빌드 통합
2. Cloudflare Workers/D1/R2 구성, 2인 초대 로그인 및 사용자별 접근 권한 검증
3. 사진 업로드/정렬/보관 및 간단한 사실정보 폼
4. Worker 연동 사진 분석→AI 원고 생성
5. 글·사진 통합 편집기/자동저장/승인
6. 네이버 복사/이미지 ZIP/발행 URL
7. 실제 카페·맛집·제품 사진으로 사용자별 end-to-end 테스트
